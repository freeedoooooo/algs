## 2. 包管理：pip / conda / 版本锁定

1. **不带版本号 = 默认升级**。`pip install xxx` 已装且非最新就会覆盖升级；想锁死写 `pip install xxx==当前版本`。
2. **conda 环境里照样能用 pip**。判断标准不是"是不是 conda 环境"，而是"会不会破坏依赖"。我这环境核心包都是 pip 装的，再用 `conda install` 有可能被求解器顺手升/降 numpy、protobuf，把 paddle 弄坏。**继续用 pip。**
3. **统一用 `python -m pip install`**。多环境时裸 `pip` 可能指向别的解释器（本机就存在 `python` 是 3.13、`pip` 属于 3.12 的情况），`python -m pip` 能保证装进当前解释器。自检：`pip -V` 与 `python -m pip -V` 路径是否一致。
4. **Python 版本约束的方向**：是「Python 先定 → pip 只挑匹配的轮子 → 包必须有对应轮子」，不是反过来。
   - paddlepaddle 3.2.0 有 `cp39/310/311/312/313` 轮子 → **支持 Python 3.9~3.13**，我落在 3.10 只是当初建环境时选的，不是被逼的。
   - 之前 `matplotlib==3.11.2` 装不上，是因为它 **Requires-Python >=3.11**，与 paddle 无关 → 退到 3.10.9。
5. **`requirements.txt` 已全部锁版本**，`pip install -r` 不会再升级 paddle。
6. **`paddle 3.2.0 outdated（最新 3.3.1）` 不用管**：那只是版本号对比提醒，不是错误。已验证组合别动；真要升，先 `conda create -n paddle331 --clone paddle` 在克隆环境里试（模型缓存在 `~/.paddlex/`，与 conda 环境无关，可直接复用）。

## 3. Paddle 三层架构（今天最重要的概念）

```
你的代码
   ↓
paddleocr 3.7.0     ← 产品层：PaddleOCR / PPStructureV3 这些开箱即用的类
   ↓ 依赖
paddlex 3.7.2       ← 产线层：多模型串流水线 + 模型文件管理 + 统一配置/结果
   ↓ 依赖
paddlepaddle 3.2.0  ← 框架层：张量、自动求导、算子（真正算数的）
   ↓
   CPU / GPU
```

一句话记：**paddlepaddle 是发动机，paddlex 是变速箱 + 零件仓库，paddleocr 是整车型（OCR 这一款）。**

`paddlex` 具体干 5 件事：
1. 产线编排（如"表格识别"= 版面检测 → 表格分类 → 结构识别 → 单元格检测 → OCR）
2. 任务模块封装（每个模型的 加载/预处理/推理/后处理）
3. **模型管理**：下载、缓存到 `~/.paddlex/official_models/`、多模型源、解压校验
4. 统一配置（`configs/pipelines/*.yaml` 决定默认用哪个模型）
5. 统一结果对象（`save_to_html / save_to_json / save_to_img`）

> **排错经验**：以后 OCR 遇到的 90% 工程问题（换模型、调阈值、离线部署、模型下载、结果导出），对象都是 **paddlex**，不是 paddleocr 也不是 paddlepaddle。

### 为什么上次会去下载 v6 模型？

**不是"自动追最新"，是"默认值变了导致缓存没命中"**：
- 默认模型名是代码里写死的映射表（`_pipelines/ocr.py`）：`lang='ch'` + 不指定版本 → `PP-OCRv6_medium`。
- 下载是**惰性按需**的：本地缓存里有就用（打印 `Model files already exist`），没有才下，**下过一次就复用，不会主动换新**。
- 升级到 3.7.0 后默认值从 v4/v5 变成 v6 → 缓存里没有 v6 → 首次实例化才去下，正好撞上 HuggingFace 连不通，看起来像卡死。

**模型源处理**：`PADDLE_PDX_MODEL_SOURCE=BOS`（百度云）+ `PADDLE_PDX_DISABLE_MODEL_SOURCE_CHECK=True` 可走国内快源。但**大文件断连会自动回退 HuggingFace**（源码没有"只锁单一源"的开关），365MB 的 `SLANeXt_wired` 就中招了。最终用 **curl 断点续传** 直下 BOS 的 tar，解压到 `~/.paddlex/official_models/{name}/` 解决问题（约 626MB）。

## 4. 性能：为什么慢 100 秒，怎么快 27 倍

加了**分段耗时日志**（加载 / 推理 / 总计）后立刻定位到真凶：

| 模型 | 加载 | 单张推理 | 总计 |
|---|---|---|---|
| `PP-OCRv5_server`（大模型） | 17.3s | **103.8s** | 121s ❌ |
| `PP-OCRv4_mobile`（移动端小模型） | ~3~7s | **3~5s** | **5.8~12.4s** ✅ |

**根因**：不是加载慢，是**没有 GPU 时在 CPU 上跑 server 大模型**。改 mobile 后精度几乎无损（照样认出"招商银行"），速度快 10~27 倍。脚本已默认 mobile，想要最高精度再换回 server 版。

## 5. PaddleOCR 3.x 的 API 坑（踩了 4 个）

| 老写法（2.x） | 3.x 正确写法 |
|---|---|
| `use_angle_cls=True` | `use_textline_orientation=True` |
| `ocr.ocr(path, cls=True)` + `result[0]` 解包 | `ocr.predict(path)`，取 `rec_texts` / `rec_scores` / `rec_polys` |
| `from paddleocr import PPStructure` | `from paddleocr import PPStructureV3`（**3.7.0 已移除 PPStructure**） |
| `import fitz`（PyMuPDF） | `import pymupdf`（1.24+ 弃用 fitz，本机 1.28.2） |

另外两个：
- `PPStructureV3` 的结果要 `res.json['res']`（多一层嵌套），表格用 `res.save_to_html()` 导出。
- **`save_to_html()` 产出的 HTML 没有 `<meta charset>`**，中文 Windows 浏览器按 GBK 解码 → 乱码。已在 `d_table_ocr.py` 加 `ensure_readable_html()` 补编码声明 + 表格样式（幂等、防 `<html>` 嵌套）。

## 6. PDF 专题（今日重头戏）

### 6.1 两个库的分工

| 库 | 干什么 | 对应脚本 |
|---|---|---|
| **pdfplumber** | 读文本层（文字 + 位置 + 表格结构），底层 pdfminer | `c_pdf_text_layer.py` 判断/抽字 |
| **pymupdf** | 把 PDF 渲染成图片（MuPDF C 库绑定），也能 `get_text()` | 扫描件转图，再交给 `b` 做 OCR |

### 6.2 PaddleOCR 拿到 PDF：一律转图，不看文本层

实测 `PaddleOCR.predict('test3.pdf')` 能跑通（2.5s 出结果）。源码链路：

```
paddlex/inference/utils/io/readers.py:314  PDFReaderBackend → pdfium.PdfDocument(in_path)
paddlex/inference/common/batch_sampler/image_batch_sampler.py:118 → 逐页 read() 成图片
渲染库：pypdfium2 5.14.0
```

`paddleocr` 包里**一行 PDF 代码都没有**，能力全来自 paddlex。**它不会先判断有没有文本层**。

### 6.3 关键发现：`test3.pdf` 是个「裁剪陷阱」

```
obj 4  /MediaBox [0 0 595 842]        ← A4 整页，内容流画满（1830 个字符，一直到 y=830）
       /CropBox  [0 699.482 595 842]  ← 只显示页面顶部 142.518pt（约 A4 的 1/6）
```

- **MediaBox**：纸张尺寸 + 坐标系基准（物理边界，页面字典里唯一必需、可从父节点继承）；
  **CropBox**：显示 / 打印的可见视口（缺省时等于 MediaBox）。
  两者都是页面元数据，与「内容流画到哪」无关，改哪个都不会增删文字。
- 我打开 PDF 只看到顶部（银行抬头 + 表头）；下方 **30+ 行流水数据真实存在但被裁掉不显示**（页脚还写着"页码 1/43"）。

### 6.4 实测：同一份 PDF，4 种工具出 4 种结果

| 方式 | 读的范围 | 结果 |
|---|---|---|
| pdfplumber `extract_text()` | 全部内容流 | **2054 字符**（0.17s，零错误） |
| pdfplumber `page.crop(page.cropbox)` | 仅可见区 | 143 字符 |
| pymupdf 默认 `get_text()` | 可见区（按 CropBox） | 144 字符 |
| PaddleOCR 直喂 PDF | 可见区（pypdfium2 按 CropBox 渲染） | 145 字符 / 19 行 / 2.5s |
| **cropbox 改成整页后渲染 → OCR** | 整页 | **1802 字符 / 226 行 / 14.1s** |

**结论**：差异不是工具质量差，而是「读全部内容流」还是「只读可见区」的选择不同。处理 PDF 前必须先明确要哪种。

### 6.5 ⚠️ 裁剪 = 隐藏，不等于删除

查文件字节结构后的判断——**不是有人手动裁剪失误，是程序化裁剪**：

| 证据 | 说明 |
|---|---|
| `%%EOF` 只有 1 次、`startxref` 1 次 | 无增量更新 → 是**一次性生成**的，不是"打开→改→另存" |
| 仅 17 个 xref 对象、无 Producer/Creator/CreationDate | 脚本/库产物（人工用 Acrobat 编辑必留 Producer） |
| `CropBox` 的 `699.482` 是非整数 | 程序算出来的，不是鼠标拖的 |

**工具做对了"显示"，但没做"清除"**：被裁掉的内容一行没删，仍完整留在内容流里，`extract_text()` 一抽就有。

> 做敏感数据处理时这非常致命——以为"裁掉了"就安全，其实别人一行代码就能复原。

真要删干净必须用**擦除（redaction）**，不是设裁剪框：

```python
page.add_redact_annot(pymupdf.Rect(0, 0, 595, 699.482))
page.apply_redactions(images=pymupdf.PDF_REDACT_IMAGE_REMOVE)
doc.save('out.pdf', garbage=4, deflate=True)
```

| 做法 | 文件里还留着吗 | `extract_text()` 能抽到 |
|---|---|---|
| 设 CropBox | **还留着** | ✅ 能 |
| redaction 擦除 | **真删了** | ❌ 抽不到 |
| 渲染成图再生成 PDF | 原文字没了（变像素） | ❌ 只能靠 OCR |

### 6.6 正确做法：先分流，再处理

1. 判断有没有文本层（抽前几页看字符数，阈值 `MIN_CHARS=50`）
2. **有** → 直接抽字：毫秒级、100% 准确、可复制、能保留坐标/字体
3. **没有**（扫描件）→ 转成图片 → 走 OCR

**有文本层但仍需 OCR 的例外**：文本层损坏/缺 ToUnicode 映射导致乱码、需要版面或表格结构还原（PP-StructureV3 必须看图）、印章/手写/公式/图表（文本层里没有）。

一句话：**OCR 是"像素 → 文字"的有损重建，能用文本层就绝不用 OCR。**

## 7. Python 基础：`if __name__ == '__main__':`

**主程序守卫**。Python 给每个 .py 文件设 `__name__`：

- 直接运行 `python xx.py` → `__name__ == '__main__'` → 条件成立 → 执行 `main()`
- 被 `import xx` → `__name__ == 'xx'` → 不成立 → **不会执行**

好处：文件既能当脚本跑，又能当模块被复用，互不干扰。没有守卫的话，别人一 import 你的文件，里面的代码就立刻跑一遍（比如当场加载模型去 OCR）。

写成 `main()` 函数而非直接写在 if 下面，还有三个好处：变量不污染全局、可被别处调用、可读性好。

> 现状：`c` 用了守卫；`b`、`d` 是平铺写法（import 它们会当场跑模型）。周末任务要把 B/C/D 串起来时，最好把 b、d 也改成守卫形式。
