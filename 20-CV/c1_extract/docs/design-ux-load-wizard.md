# design-ux-load-wizard — 入库＋模板可用性改造：第一步「统一叙事」＋第二步「入库向导」

状态：**已实施（2026-11-22，第一、二层全部落地）**。决策已拍板：D1＝加只读 dry-run 端点 `POST /api/tasks/{id}/load-preview`；D2＝独立 `web/wizard.js`＋`wizard.css`；D3＝后端中文文案本轮改齐（需重启 8765 生效）；D4＝入库页保留并改名「入库规则（高级）」。范围＝此前讨论的三层方案中的第一、二层；第三层（入库规则版本化，解决模板新版本→映射整表重配的结构性痛点）不在本文，另行设计。

## 〇、大白话版（先看这段）

### 现在的问题

数据要进业务库，用户实际要做对两件事，但界面把这两件事拆成了三个陌生页面：

```
原件文件 ──[模板]──▶ 一串字段（校验台账里的记录） ──[入库配置]──▶ 业务库的表列
           模板页：怎么读                入库页：字段放到哪
```

术语多、撞词（两个"映射"、三个"表"）、页面是"配置总表"而不是"我该干什么"。

### 改完之后（用户视角）

以审计员小李入库一批银行流水为例：

1. 提取页上传 3 份流水 PDF，选了模板「银行流水 v3」→ 建任务。
2. 页面顶部始终有一条**流程条**：`原件 → ① 提取 → ② 校验 → ③ 入库`，当前环节高亮，点下一步就跳过去——不再有"进来不知道干嘛"。
3. 校验页把 38 条记录确认完，按钮变成「入库」→ 点开**四步向导**：
   - 第 1 步 **选目标**：以前配过的规则直接选（"上次进 co_dev.t_bank_flow 用过，再来一次？"）；没有就选业务库＋表。
   - 第 2 步 **字段对齐**：系统按名字自动把 12 个字段对上 10 个列，只剩 2 个下拉要人选，每行有 ✓/？徽标。
   - 第 3 步 **过目**：前 3 条记录样例＋列存在性检查通过；（可选）预告"将新增 30 行、覆盖 8 行、跳过 1 行"。
   - 第 4 步 **执行**：进度和回执（沿用现有回执抽屉）。
4. 原「入库配置」页改名为「入库规则（高级）」，保留给批量管理与清理。

全站一次改齐的用词：数据源→**业务库**、入库映射→**入库规则**、业务键→**去重依据**、upsert/insert/update→三句人话。

**不改动**：数据库模型、API 路径、后端校验/预检/绑定语义、回执结构。

## 一、第一步：统一叙事（纯前端，刷新即生效）

### 1.1 流程条组件（shell.js + shell.css 新增 `flowBar`）

- 文案与节点：`原件 → ① 提取 → ② 校验 → ③ 入库`。
- 链接：原件→/sources，①→/，②→/staging，③→任务上下文向导 / 规则页（见 1.2）。
- 显示页面：提取、校验、入库三页的 pagehead 下方；任务/资料/模板不显示（辅助页）。
- 高亮规则：有 task 参数（校验工作台）＝②；台账入口＝②；入库页＝③；提取页＝①。当前节点不可点，其余可点。
- markup 约定：`<div class="flowbar" id="flowbar" data-cur="2"></div>`，shell.js 统一渲染（六页共用，禁止各页自绘）。

### 1.2 全站文案改齐清单（一次改完，不允许页面间混用新旧词）

| 旧词 | 新词 | 出现位置（逐一替换） |
|---|---|---|
| 数据源 | 业务库 | load 页卡片标题/按钮（新建业务库）/抽屉标题/空态/错误文案、入库目标抽屉、README 不变（代码注释保留旧词一次过渡） |
| 入库映射 | 入库规则 | load 页右表标题、抽屉、按钮（新建规则）、导航副标题 |
| 业务键 | 去重依据 | 规则抽屉勾选列、右表列名 |
| upsert | 「已存在的行覆盖更新，不存在的新增」 | 写入模式下拉、右表显示、回执展示（存库值不变，仅显示层映射） |
| insert | 「全部当新行插入，重复照插（靠回执可查）」 | 同上 |
| update | 「只覆盖已存在的行，对不上号的不动」 | 同上 |
| 入库配置（页名） | 入库规则（高级） | 页面 h1；导航仍叫「入库」 |
| 模板（页内说明） | 模板＝怎么读这份文件；产出＝字段 | 模板页 pagehead 一句说明、编辑抽屉分区标题 |

- 边界：**只改前端文案**。后端返回的中文错误串（如预检 400 消息）本次不动（改动需重启 8765，单列为决策点 D3）。
- 去重依据三句人话旁各加一行小字例子（"例如：发票号"）。

### 1.3 规则抽屉字段自动对齐（load.js）

- 拉列成功后（现 `loadColumns`），客户端自动匹配：字段名与列名做规范化（去空格/下划线、小写）后**全等**的，直接选中目标列并打 ✓（灰底，可改）；未命中的打 ？（红字下拉）。
- 顶部计数条：`已自动匹配 N/M 个字段，剩 K 个待确认`。
- 匹配纯前端实现，无新接口。

### 1.4 模板抽屉「这些字段去了哪」（templates.js，低成本增强）

- 编辑抽屉字段区每行尾部追加目标列提示：客户端拉 `/api/load/tables` 过滤 `template_id==当前`，把 `target_column` 并排显示；无规则则显示「未配置入库」。
- 目的：让两段配置在视觉上接成一条链（回应"隐形契约"问题）。

## 二、第二步：入库向导（任务驱动，四步）

### 2.1 入口（替换现有「入库目标抽屉」，二者不并存——统一性令）

1. 校验工作台（staging，全部确认且未入库）：「入库」按钮 → 向导。
2. 校验台账任务行：状态已确认的 → 详情侧「入库」入口 → 向导。
3. 任务详情抽屉：原「入库」按钮 → 向导。

### 2.2 向导状态机（新文件 web/wizard.js＋wizard.css，shell 挂容器；或并入 shell.js，见决策点 D2）

```
step1 选目标          step2 字段对齐        step3 过目             step4 执行
已有规则？──是──▶ 直接跳 step3     复用 1.3 组件     样例前3条＋预检        POST /api/tasks/{id}/load
   │否                                   （校验表/列/覆盖）      （绑定＋预检＋起线程＝现契约）
业务库＋目标表 ──▶ 选/新建规则草稿 ──▶                    （可选：预测计数，D1）   轮询 load-log → 回执抽屉
```

- 步进可回退；step4 前一切只是前端状态，**不落库**——保持"全过才绑定"的既有语义（service.launch_load 不动）。
- step1 命中已有规则的判定：`datasource × 任务模板` 匹配（与现入库目标抽屉同规则）。
- step3 样例来源：staging 页已加载的记录数组直接传入；从任务页进入则复用 `/api/tasks/{id}/extract?file=` 取前 3 条。
- 新建规则在 step4 成功后走现有 `POST /api/load/tables` 落库（字段/去重依据来自向导状态），失败不产生孤儿规则。

### 2.3 保持不变（技术契约红线）

- `/api/tasks/{id}/load` 的绑定语义、失败不落绑定、回执与隔离行、密码永不回显、任务已绑定的锁语义。
- 数据库表结构、API 路径、字段命名（write_mode 存库值 upsert/insert/update 不变）。

## 三、验收（轻量，按"不卡验证"约定）

- 前端为主：node --check＋浏览器只读点查——流程条三页高亮正确；新旧词全站扫描无残留（grep 清单）；自动匹配徽标在 1 个真实模板上正确；向导 golden path 一次（temp 端口，不碰 8765 真实数据）。
- 不动后端时不跑套件（沿用前端轮先例）。

## 四、决策点（实施前需拍板）

- **D1 预测计数**：step3「将新增 X/覆盖 Y/跳过 Z」需新增只读 dry-run 端点（查目标表逐条分类，约一个小函数）。要吗？不要则 step3 只有样例＋检查通过，计数在回执里看。
- **D2 向导载体**：独立 wizard.js（推荐，可控）vs 继续塞 shell.js（已 300+ 行）。
- **D3 后端文案**：服务端错误消息里的「映射/数据源」等旧词，本轮不动（免重启）还是顺带改齐（改完需你重启一次 8765）？
- **D4 入库页去留**：推荐保留为「入库规则（高级）」；也可批量管理需求弱时隐藏导航入口只留向导。

## 五、不在范围

- 规则版本化/模板版本联动增量对齐（第三步，另行设计）。
- API/DB 改动、引擎/提取侧改动、权限与身份字段（平台化另议）。
