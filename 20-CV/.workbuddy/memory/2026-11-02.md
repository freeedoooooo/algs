## week-01 真机调试：性能 & 3.x 兼容
- **CPU 上 server 模型极慢**（实测 test2.jpg 2657×609）：PP-OCRv5_server 推理 103.8s；换 PP-OCRv4_mobile 仅 3.8s（快约 27×，精度基本不损）。结论：无 GPU 默认用 mobile 模型。b_ocr_image.py 已默认 mobile，并加分阶段耗时日志（模型加载/推理/总计），实测总耗时 121s→12s。
- 3.7.0 默认模型映射表在 `paddleocr/_pipelines/ocr.py`：`lang='ch'`→PP-OCRv6_medium（升级包才变默认，非"自动追新"）；已下过就缓存复用。
- **d_table_ocr.py 适配 PPStructureV3**：3.7.0 已移除 `PPStructure`（hasattr=False），只有 `PPStructureV3`。新脚本用 `.predict()` + `result.save_to_html()`，关掉 formula/chart/seal/region，文本锁 v5。PP-StructureV3 是重流水线：需版面检测(PP-DocLayout_plus-L)、表格分类(PP-LCNet_x1_0_table_cls)、有线结构(SLANeXt_wired~365MB)、无线结构(SLANet_plus 已缓存)、有线/无线单元格检测(RT-DETR-L_*_table_cell_det)。
- 模型源：`PADDLE_PDX_MODEL_SOURCE=BOS`(百度云) + `PADDLE_PDX_DISABLE_MODEL_SOURCE_CHECK=True` 可走国内快源；但大文件(365MB)传输断开会**自动回退 HuggingFace**（源码 official_models.py 无"只锁单一源"开关）。补救：curl 断点续传直下 BOS tar → 解压到 `~/.paddlex/official_models/{name}/`（目录含 inference.json/pdiparams/yml 即命中缓存）。

## HTML 导出乱码坑（paddlex save_to_html）
- 现象：控制台/日志中文正常，浏览器打开 output/table_out.html 乱码。
- 根因：`paddlex HtmlWriterBackend` 写文件用 utf-8（字节正确），但 `_to_html()` 产出的只是 `<html><body><table>...` **片段，无 `<head>`、无 `<meta charset>`**；中文 Windows 浏览器默认按 GBK 解码 → 乱码。
- 修复：d_table_ocr.py 加 `ensure_readable_html(path)`，save 后读回检查；无 charset 则剥离重复的 html/body 外层标签，套上 `<!DOCTYPE>` + `<meta charset="utf-8">` + 表格边框 CSS 后写回。已实测（单 html/body/charset 各 1，666 bytes，无嵌套）。
- 通用教训：任何由 paddlex `save_to_html` / `save_to_json` 产出的文件都要留意编码声明与 BOM；以后其他周脚本导出 HTML 复用同一函数。
