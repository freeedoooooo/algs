## 方案评估：一任务一文件 / 取消任务表（同日 20:20，仅咨询未改代码）
- 用户新思路：解析限制只能一个文件；任务表多余，任务信息整合进文档附件表 c1_doc_file；工作台查任务改查文档表。
- 核对事实：c1_task 承载 state/error/rule_version_id(抽取时绑)/params_json/load_datasource_id/load_table_id/时间戳，是 task_id 血缘锚点（贯穿 staging_record/load_log/quarantine/业务表三列）；c1_task_file 承载每文件 state+file_id，rollup 上卷任务态；c1_doc_file 是 sha256 去重原件登记(files.py register_file)。工作台 home.js/tasks.js 均 fetch /api/tasks 取进度/规则/入库目标。file_pipeline 靠"一文件多 task 链路"做流程追踪。

## 上传"还是不行"二次排障（22:55，真根因）
- 用户澄清是**单文件上传也不行**（资料页「上传登记」，POST /api/sources）。后端实测 200 正常，8765 静态 JS 也是最新版——问题在前端执行。
- 真根因：sources.js 的 picker.onchange 写成 `var fs=this.files; this.value='';` —— this.files 是 FileList **引用**，先存引用再清空 input 会把 FileList 一起清空，fs.length=0 直接 return，用户看到"上传没效果"。home.js/parse.js 是同步先处理再清空，无此问题。
- 修复：`var fs=Array.prototype.slice.call(this.files||[]); this.value='';` 先做数组快照。已验证 8765 提供的 sources.js 含修复；端到端登记→列表可见→清理全通过；dev 库 doc_file 归零。
- 教训：FileList 是引用类型，input.value='' 会清空它；任何"先存 files 再重置 input"的写法都必须先 slice 成数组。这解释了为何之前 curl 测 API 全 200 但浏览器端无效——纯 API 验证抓不到前端引用清空 bug。
