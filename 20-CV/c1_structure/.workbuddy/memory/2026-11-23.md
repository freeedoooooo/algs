## 咨询：入库数据的血缘回溯方案（未立项，仅设计建议）
- 用户问：预览已有逐格血缘（c1_staging_lineage），入库后如何回溯；业内主流怎么做。
- 现状盘点：预览血缘 = c1_staging_lineage（record_id+field_name+page+cell_bbox+raw_text）；入库回执 = c1_load_log（task_file_id+record_index+datasource_id+target_table+target_pk+action），二者靠 (task_file_id, record_index) 软连接；loader.write_record 的 pk 在 insert 时是 lastrowid、upsert 时是业务键 JSON。
- 建议（分层，均未实现）：①回执扩为不可变证据包，写入时冻结 rule_version_id / 映射快照 hash / transform 版本 / 写入值 hash / before-after / 单元格快照；②业务行加稳定身份 _c1_row_uid（可选列，对标 Iceberg V3 _row_id）；③回执哈希链做 tamper-evident；④运行级 OpenLineage RunEvent（Marquez/DataHub 消费）与记录级证据链分离。
- 关键坑：现有 uk_load_receipt 幂等唯一键 skip 会吞掉血缘更新；重抽按 task_file 先删后插会让 record_index 复用导致血缘漂移；入库目标禁选平台 c1_* 表（既有警示）。
- 业内结论：目录型（OpenLineage/DataHub/Atlas/Unity Catalog）止于 dataset/column 级；record 级 provenance 需自建（W3C PROV 词汇层 + 写入时采集），Iceberg V3 才有原生 row lineage；QLDB 已于 2025-07-31 退役。
